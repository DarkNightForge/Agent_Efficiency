# Agent_Efficiency

**Agent_Efficiency gives a coding agent data that always existed but that it
never saw while it worked: what it has spent, how fast, and how much of the usage
window is left.**

![usage-budget in action](docs/demo.gif)

<sub>Real CLI output, synthetic usage data — regenerated by
[`claude-code/demo/`](claude-code/demo/), never recorded from a live session.</sub>

Claude Code already logs every turn to disk with a full token breakdown, and it
already hands its status line the account's 5-hour and weekly usage percentages.
None of that reaches the model, so an agent on a subscription plan burns the
window dry mid-task and you find out when it stops. This project reads both,
rebuilds the spend from the transcripts, and injects the result into every
prompt. The agent knows your burn rate and how much of the window is left, warns
you before a big task that won't fit, and says when there is room to go wide.

Token counts are exact, and so are the usage percentages while a status line
reading is fresh (under 15 minutes old). Dollar figures are estimates:
list-price weights standing in for however the limiter actually scores usage.

Getting there meant measuring what Claude Code actually writes rather than
assuming. It writes one transcript record per *content block* of a reply, each
repeating the reply's whole `usage` payload, so counting records inflates spend
~2.4x (FINDINGS §11). And a window boundary is server state: a 5-hour window
opens with the first message on the *account*, not on this machine, so the tool
takes reset times from the meter instead of computing them (FINDINGS §4c, §14).
Both are in [`docs/FINDINGS.md`](docs/FINDINGS.md).

Codex serves its rate limits directly, through the App Server's
`account/rateLimits/read`, so the [Codex implementation](plugins/agent-efficiency/),
ported to Codex by [@Eclipse1231317](https://github.com/Eclipse1231317), reads
them instead of reconstructing them. The [Hermes implementation](hermes/) reuses
Hermes's own provider meter and injects a replay-safe policy block through its
plugin lifecycle. The block, as the Claude implementation renders it:

```
<usage-budget>
5h window: ~14% used ($84.00 of ~$600.00 weighted) · ~$516.00 left · resets 22:00 (in 1h 35m)
Burn: $73.00/h (last 24m) → 5h window caps in ~7h 04m, resets in 1h 35m
Week: ~26% used ($780.00 of ~$3000.00) · ~$2220.00 left · resets Mon 07:00 (in 106h 35m)
Week pace: day 2/7 — $780.00 of $857.14 allowed by now (91% of today's share, on pace)
Affordance: ~1961 more turns at $0.095/turn (median this window) · a 16 agents x 12
turns fan-out costs ~$10.92, ~7 fit · binding: week pace
Confidence: low (1 calibration). Recalibrate from /usage if this looks off.
How to use: … If a task's likely spend exceeds the remaining headroom, say so
before starting and offer a smaller scope or a cheaper model.
</usage-budget>
```

Now the model can plan against a budget, and push back on work that won't fit.

### It has to point both ways (FINDINGS §13)

Every signal above except `Affordance:` is a brake. That is a bias, not caution:
**unspent allowance expires at the reset and buys nothing**, so a window closed at
4% used is a worse answer the user already paid for — the mirror image of running
the week dry on Tuesday. This project had already measured the over-braking
failure once (an agent shortened its own plan with 53% of the window unspent)
before noticing the signal set could only ever produce more of them.

So there is an affirmative direction with a real threshold:

```
GO WIDE: headroom is ample and the week is under pace. Prefer the more thorough
approach — parallel subagents, wider verification, deeper search. Do NOT cut
scope to save usage; unspent allowance expires at the reset and buys nothing.
```

...and one place the tool asks instead of reporting, once the week passes the
share of it that has elapsed:

```
ASK BEFORE PROCEEDING: the week is at 120% of day 3/7's share, and at $360.00/day
it runs dry on day 5/7, blocking the last 2 day(s) of the week. Before starting
substantial work, call AskUserQuestion with … continue at full scope · reduce
scope or drop to a cheaper model · stop and resume after the reset. This is a
checkpoint, NOT a refusal.
```

It fires once per day, and again only if the overshoot worsens by ≥25 points — a
prompt that can fire every turn gets approved without being read.

## The core idea (Claude Code)

> **Spend is exactly computable from local logs. Capacity is unpublished, so it is
> back-solved from the usage percentage.**

Every turn your agent takes is logged locally with a complete token breakdown, so
*spend* is computable to the cent, provided you count **messages, not transcript
records**: deduplicate on `message.id`. That is a claim to validate, not assume.
Counting records overstates spend ~2.4x, and `/usage` prints per-conversation
token totals that make the check free (FINDINGS §11).

What's unpublished is *capacity*, so the tool back-solves it from a usage
percentage:

```
capacity = spend_in_window / (percent_shown / 100)
```

The percentage comes from Claude Code's status line, which receives the
account's 5-hour and weekly `used_percentage` and `resets_at` after each reply on
Pro and Max plans ([status line docs](https://code.claude.com/docs/en/statusline)).
`install.sh` wires `usage-budget statusline` into it, wrapping any status line
you already have. A reading older than 15 minutes is not served as exact. The
block then falls back to a capacity calibrated from a `/usage` reading, marks its
figures as estimates, and reports a confidence level based on how well repeated
calibrations agree.

Codex does not need to pretend it has the same data source. Its plugin accepts
App Server `usedPercent`, window duration, and reset data, then keeps measured
usage visibly separate from estimated future-task cost.

Each implementation is owned by whoever's agent runs on that provider. That isn't
just convenience: an agent running on the provider it measures can **empirically
verify** that provider's behavior. The Claude Code implementation could not check
its own limits and shipped two wrong assumptions as a result — both caught only by
comparing against a real usage reading. Self-verification is the difference between
measuring and guessing.

The implementations are independent programs sharing one set of findings. They deliberately use
the same language for measurements, estimates, confidence, and how long running
out would block you, while remaining native to what each host actually exposes.

## Quick start (Hermes)

```bash
git clone git@github.com:DarkNightForge/Agent_Efficiency.git
cd Agent_Efficiency/hermes
./install.sh
```

Start a new Hermes session, then run `/agent-efficiency refresh`. Standard OpenAI
Codex (`codex_responses`) and OpenRouter are supported. A Claude subscription
login in Hermes is not: Anthropic's terms reserve that login for Claude Code and
Anthropic's own apps ([legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)).
The plugin requires the route-aware, multimodal sidecar host contract documented
in [`hermes/README.md`](hermes/README.md). Hermes's optional native
`codex_app_server` transport does not currently deliver plugin `pre_llm_call`
context and is therefore explicitly unsupported.

## Quick start (Codex)

Clone the repo, add it as a local marketplace, then install the plugin:

```bash
git clone git@github.com:DarkNightForge/Agent_Efficiency.git
cd Agent_Efficiency
codex plugin marketplace add "$PWD"
codex plugin add agent-efficiency@agent-efficiency
```

Start a new Codex task after installation. Ask:

```text
Show the Agent Efficiency control center for this task.
```

That opens one place showing all three modes, what each mode will actually do,
its time and token estimate, and any available usage-capacity estimate. Pick a
card and use it for this task, or save it as the default.

The three modes are intentionally blunt:

- **Throughput** wants the task done as soon as practical. It uses relevant tools,
  safe parallel work, retries, and strong validation readily. It usually spends
  the most tokens and allowance.
- **Balanced** balances speed, usage, and confidence. It reads focused context,
  makes targeted changes, and validates in proportion to the risk. This is the
  default.
- **Stretch** minimizes tokens and tool calls. It reads narrowly, avoids
  optional fan-out, stays concise, and runs the smallest sufficient validation.
  It may take longer.

By default, only the selected mode is calculated. That avoids spending extra
thinking time estimating two modes you may not use. To compare all three, ask:

```text
Compare all three Agent Efficiency modes for this task.
```

To change the persistent default, ask `Set Stretch as my default Agent
Efficiency mode` (or choose **Set as default** in the control center). A mode
picked with **Use selected mode** affects the current task without silently
changing the default.

You can also be direct: `Use Throughput for this task`, `Use Balanced for this
task`, or `Use Stretch for this task`. The plugin times completed work, records
numeric token and tool metadata, snapshots each starting forecast, audits it
against measured outcomes, and uses comparable residual error to calibrate later
estimates and confidence. It does not store prompts, responses, file contents,
or tool arguments.

Capacity has two different kinds of numbers, and the UI labels them separately:
the current usage percentage comes from a Codex App Server snapshot refreshed
by trusted hooks and explicit control-center requests; tasks remaining and
time-to-cap are estimates. A snapshot older than five minutes is rejected rather
than presented as current. Refresh failures preserve the last snapshot without
relabeling stale data as live. Until enough completed-task history
exists, the plugin says `UNCALIBRATED` or clearly marks a first-use heuristic.

After installation, open `/hooks`, review the Agent Efficiency commands, and use
Codex's supported trust control. Trust is never bypassed.

**Historical v0.1 baseline, measured on Codex `0.148.0-alpha.9`:**

1. The first v0.1 build installed hooks as `trustStatus=untrusted`, so they did
   not fire until manually trusted. The current instructions now document that
   supported trust step.
2. The first v0.1 build did not fetch rate-limit snapshots. The current Codex
   App Server client performs the authenticated read through hooks and explicit
   refresh requests.

Modes, ETAs, and the CLI control center continue to work when telemetry is
temporarily degraded. See
[`codex/README.md`](codex/README.md) and [FINDINGS §9b](docs/FINDINGS.md#9b-codex-the-second-provider-and-the-first-test-of-what-generalizes).

> Exact messages remaining cannot be calculated because messages do not have a
> fixed usage cost. Estimates also depend on the plan and active limit window,
> model, context, task complexity, execution location, token composition, tools,
> speed setting, media, shared activity, and the expected profile of future work.

## Quick start (Claude Code)

### Easiest: let your agent install it

Paste this into Claude Code and it will do the whole thing — clone, install,
wire the hooks, calibrate, and verify. It will ask before it touches anything.

```
Read and follow every step of:
https://raw.githubusercontent.com/DarkNightForge/Agent_Efficiency/main/BOOTSTRAP_FOR_AGENTS.md
Goal: install usage-budget so you can see how much of my subscription window is
left and pace long work against it. Ask me before writing anything. Never invent
calibration numbers — get them from my /usage screen. You are not done until
`usage-budget verify` exits 0.
```

The finish line is machine-checkable on purpose: `usage-budget verify` exits `0`
only when the next turn will actually carry a usable budget block, so the agent
cannot mistake an encouraging transcript for a working install.

### Or do it yourself

```bash
git clone git@github.com:DarkNightForge/Agent_Efficiency.git
cd Agent_Efficiency/claude-code
./install.sh            # symlinks the CLI, wires the hooks and the status line, prints next steps
```

If you already have a status line, `install.sh` wraps it rather than replacing
it: your command still runs and gets the same input, and `settings.json` is
backed up first.

`install.sh` also installs a **skill** that teaches the agent when to act on the
injected block — and, just as importantly, when to stay quiet. Injecting numbers
into context does not change behavior on its own; see
[`docs/PORTING.md`](docs/PORTING.md#the-skill-is-not-optional).

Once Claude has replied in a session, the block carries the vendor's own
percentages. For the stretches when that reading is stale, calibrate once: run
`/usage` in an interactive session, read the numbers, and tell the tool:

```bash
usage-budget calibrate --pct 13 --resets "10:00pm" \
                       --weekly-pct 26 --weekly-resets "Aug 17 7:00am"
```

Enter reset times exactly as `/usage` shows them. A reset ending in `:59` is
real: the API returns `HH:MM:59`, so don't round it up to the hour (FINDINGS §15).

With neither a fresh reading nor a calibration, it reports raw spend and says
`UNCALIBRATED` rather than inventing a denominator.

If your account has extra-usage credits turned on, say so once:

```bash
usage-budget extra-usage on
```

Without that, the tool assumes hitting a cap stops you.

Either way, confirm the install actually works:

```bash
usage-budget verify        # exits 0 only when the next turn gets a real block
```

## What this is not

- **Not billing.** Figures are list-price-*equivalent* weights used as a proxy for
  however the limiter actually scores usage. On a subscription they're a unit of
  account, not money owed.
- **Not authoritative.** The vendor's usage UI always wins. This is a planning aid
  between readings.
- **Not a way to exceed limits.** It helps you spend a fixed budget deliberately
  instead of accidentally.

## What the Claude implementation can't see

- **Per-model weekly caps.** A separate weekly limit on one model isn't in the
  status line's data, so it isn't tracked. `/usage` shows it.
- **Whether extra-usage credits are on.** Declare it with
  `usage-budget extra-usage on` or `off`. Left unset, the tool assumes a cap is a
  hard stop and warns about lockouts on that basis.

## Design principles

1. **Separate the exact from the estimated, visibly.** Never present a calibrated
   guess as a measurement.
2. **Degrade to silence, not to confidence.** Expired or missing calibration
   yields `UNCALIBRATED`, never a stale number dressed as current.
3. **A forecast beats a percentage.** "Cap in 40m, reset in 2h — cap arrives
   first" is actionable; "63% used" is not.
4. **Never block the host.** Every failure path in the injection hook is
   swallowed. A broken budget tool must not break a prompt.
