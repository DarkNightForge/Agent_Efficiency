# Behavioural evals (E4)

The unit suite (174 tests) asserts what the `<usage-budget>` block **says**.
Nothing asserted what a model **does** with it — which is the only thing this
project exists to change. A block that renders perfectly and is then ignored, or
obeyed too hard, is a failure the arithmetic cannot see.

```bash
python3 evals/run_evals.py                  # all scenarios, n=3
python3 evals/run_evals.py -n 5             # more samples
python3 evals/run_evals.py --with-skill     # SKILL.md in the system prompt
python3 evals/run_evals.py -s silence-ample --save out.json
python3 evals/run_evals.py --dry-run        # print prompts, spend nothing
```

Not part of `unittest discover` — it needs a model, a network, and real money.
The unit suite stays stdlib-only and offline.

## Four things this harness had to get right

**1. Isolation (`--bare`).** Without it, evals run inside your own hooked
environment and the *real* usage-budget hook injects live figures next to the
fixture. Measured: the model answered from the live numbers and ignored the
fixture completely. `--bare` skips hooks — and incidentally drops the system
prompt from ~42k to ~1.7k cached tokens, taking a run from ~$1.50 to ~$0.06.

**2. Repetition.** Sampled models are stochastic. Two scenarios passed one run
and failed the next with no code change in between. A binary verdict from n=1
would have sent someone editing a feature that was not broken, so the harness
reports a **rate** and defaults to n=3.

**3. Answerable tasks.** Tools are limited, so a task must be answerable from the
prompt alone. An early version asked the model to audit "this repository" while
the cwd was an empty temp dir; the model correctly reported there was nothing
there, and the eval measured nothing at all.

**4. Graders that match behaviour, not phrasing.** One grader accepted only
`stop|resume|after the reset|wait` and failed a response offering to *"hold until
the reset"* — correct behaviour, wrong synonym. A grader that fails good
behaviour is worse than no grader, because it invites fixing the feature to
satisfy the test.

## Fixtures

Generated by the real `render_inject`, not pasted, so they cannot drift from the
implementation. What they say is already locked down by the unit suite; what a
model does with them is what these measure.

## Grading: assertions, not substrings

`must_not_match` is evaluated only against sentences that **assert**. A model
saying *"I can't tell you whether that's 10% or 90%"* is declining to quote a
percentage; a substring grader saw `90%` and reported a defect that did not exist
(§18). The disclaimer cue list is deliberately narrow — a false negative hides a
real defect, a false positive only wastes a re-read — and every removed cue has a
test in `tests/test_evals_grader.py`.

`must_match` is *not* filtered: it asks whether something was communicated, and a
hedged sentence still communicates.

## Reading a failure

A failure is **not** necessarily a model bug. It is just as likely a block that
does not say what it meant to, a task that cannot be answered, or a grader
over-fitted to wording. Read the response — `--save` writes them all — before
changing anything. Four of the first five failures here were harness bugs — three in §16, one in §18.
Always use `--save`: it lets a grader correction be a re-read instead of a re-run.
